# Architecture Research

**Domain:** Rust-core / thin-native-shell Android port of a desktop `egui` app (via `android-activity`), needing a foreground Service, MediaSession, AudioManager focus, and Keystore-backed credentials.
**Researched:** 2026-10-14
**Confidence:** MEDIUM (core JNI/context patterns are HIGH confidence from official `docs.rs` sources; service/MediaSession wiring and crate maturity are MEDIUM/LOW — no single reference project does exactly this combination, so the design below is synthesized from verified primitives, not copied from one proven example)

### Component Responsibilities

| Component | Responsibility | Typical Implementation |
|-----------|----------------|-------------------------|
| `MainActivity` (generated by packaging tool) | Hosts the `android-activity` NativeActivity/GameActivity surface; owns app lifecycle events (`onResume`/`onPause`/`onDestroy`) that `android_main` consumes via `AndroidApp` | Mostly unmodified boilerplate from the chosen packaging tool (cargo-apk2 / cargo-ndk+Gradle / xbuild). No Spotify logic here. |
| `PlaybackService` (new, Kotlin/Java, ~100-200 LOC) | Real `android.app.Service` (or `androidx.media3.session.MediaSessionService`) that Android's process-lifecycle manager is actually allowed to keep alive in the background; owns the `MediaSession`/`MediaSession.Callback`, builds the foreground notification, requests/abandons `AudioManager` focus | Small Kotlin class; forwards every user-facing callback (`onPlay`, `onPause`, `onSkipToNext`, `onAudioFocusChange`) into Rust via `external fun`; exposes a couple of Rust→Kotlin JNI entry points for updating notification/session metadata |
| `src/android/jni_bridge.rs` (new, Rust) | Rust-initiated calls into Java APIs that don't require subclassing (AudioManager, NotificationManager, KeyStore, Cipher, SharedPreferences) | Uses `ndk-context::android_context()` + `jni` crate: get `JavaVM`, `attach_current_thread()`, `call_method`/`call_static_method` |
| `src/android/service_bridge.rs` (new, Rust) | Exposes `#[no_mangle] extern "system" fn Java_<pkg>_PlaybackService_...` entry points that the Kotlin shim calls; translates them into `Action`s or direct calls into `backend.rs`/`player.rs` | Thin adapter layer only — no business logic, same rule as `src/ui/` emitting `Action` |
| `src/android/credentials_android.rs` (new, Rust) | Implements the `keyring-core` `CredentialStore`/`Credential` traits for Android, so `credentials.rs` gains an Android arm alongside its existing macOS/Windows/Linux providers | Pure JNI (no Kotlin class): drives `java.security.KeyStore` ("AndroidKeyStore" provider), `KeyGenParameterSpec.Builder`, `Cipher`, and `SharedPreferences` for the ciphertext blob — all concrete/static Java SDK classes, no callback interfaces needed |
| `src/backend.rs` / `src/player.rs` (existing, unmodified) | Owns the tokio runtime, librespot session, playback engine; never runs on UI thread today and must not change for Android | Existing code; Android only adds callers (JNI bridge) and a couple of state-change hooks for the notification/MediaSession to read |
| `src/ui/` / `src/app.rs` (existing, unmodified) | Draws and emits `Action`; applies `Action` | No Android-specific change expected beyond touch-layout work from Phase 3 |

## Recommended Project Structure

```
src/
├── android/                 # NEW — all Android platform glue, cfg(target_os = "android")
│   ├── mod.rs                # wiring: registers the module, re-exports entry points
│   ├── jni_bridge.rs          # Rust → Java: AudioManager, NotificationManager helpers
│   ├── service_bridge.rs      # Java → Rust: Java_<pkg>_PlaybackService_* exported fns
│   ├── credentials_android.rs # keyring-core CredentialStore impl via AndroidKeyStore
│   └── lifecycle.rs           # maps android-activity AndroidApp events → existing app.rs hooks
├── ui/                       # unmodified
├── app.rs                    # unmodified
├── backend.rs                # unmodified (tokio runtime, networking)
├── player.rs                 # unmodified (playback engine)
└── credentials.rs            # existing dispatcher; gains one more `cfg(target_os = "android")` arm

android-shell/ (or wherever the packaging tool puts it, e.g. an `android/` Gradle module)
├── AndroidManifest.xml        # declares PlaybackService, FOREGROUND_SERVICE* permissions
└── src/main/java/<pkg>/
    └── PlaybackService.kt     # the one Kotlin class described above
```

### Structure Rationale

- **`src/android/` mirrors the existing per-platform convention already used for `tray`, `window.rs`, `power.rs`, etc.** — Android becomes one more `cfg`-gated module family, not a parallel app.
- **The Kotlin shim is deliberately isolated to a single class (`PlaybackService`)** plus whatever manifest entries the packaging tool requires. Everything that doesn't strictly require subclassing an Android base class (`Context.getSystemService` lookups, `KeyStore`, `Cipher`, `SharedPreferences`, building an `Intent`) is called directly from Rust via `jni` + `ndk-context`, per the project's "smallest possible native code" rule (R7).
- **`credentials_android.rs` has no Kotlin counterpart** because every Keystore-related class (`java.security.KeyStore`, `KeyGenParameterSpec.Builder`, `Cipher`, `SharedPreferences`) is concrete/instantiable and requires no interface implementation — a pure JNI shim from Rust is sufficient and standard.

## Architectural Patterns

### Pattern 1: Rust calls Java directly via `jni` + `ndk-context` (no shim class)

**What:** For any Android API that's a plain method/static call on an existing object (not a callback interface you must implement), call it straight from Rust using the globally available `JavaVM`/`Context` that `android-activity` already registers with `ndk-context` before `android_main` runs.
**When to use:** `AudioManager` lookups, `KeyStore`, `Cipher`, `SharedPreferences`, building and sending `Intent`s (e.g. `startForegroundService(intent)`), reading system properties.
**Trade-offs:** No extra Kotlin/DEX compilation step, keeps the "native code is Rust" principle. Downside: verbose, stringly-typed JNI signatures; must hand-attach the current thread when called off the `android_main` thread (e.g. from a tokio worker thread) and detach correctly to avoid JVM thread-table leaks.

**Example (verified against the official `ndk-context` docs — HIGH confidence):**
```rust
let ctx = ndk_context::android_context();
let vm = unsafe { jni::JavaVM::from_raw(ctx.vm().cast()) }?;
let mut env = vm.attach_current_thread()?;
let class_ctx = env.find_class("android/content/Context")?;
let audio_service = env
    .get_static_field(class_ctx, "AUDIO_SERVICE", "Ljava/lang/String;")?;
let audio_manager = env
    .call_method(
        ctx.context() as jni::sys::jobject,
        "getSystemService",
        "(Ljava/lang/String;)Ljava/lang/Object;",
        &[audio_service.borrow()],
    )?
    .l()?;
```

### Pattern 2: Thin Kotlin/Java shim class for anything requiring subclassing

**What:** A minimal Kotlin class (`PlaybackService extends Service`, implementing `MediaSession.Callback` and `AudioManager.OnAudioFocusChangeListener`) because Android requires a real subclass instance for: (a) anything the OS lifecycle manager needs to track and keep alive (a `Service`), and (b) any callback interface (`MediaSession.Callback`, `OnAudioFocusChangeListener`) — JNI cannot synthesize an anonymous Java subclass from Rust at runtime.
**When to use:** Foreground Service registration, MediaSession transport-control callbacks, audio-focus-change callbacks, notification posting that must survive process/Activity teardown.
**Trade-offs:** Requires compiling at least one `.kt`/`.java` file and packaging DEX bytecode — which constrains the packaging-tool choice (see Build Order below). Keep this class a pure forwarder: every callback body should be one line calling into Rust via `external fun`, with no business logic in Kotlin (mirrors the existing `src/ui/` → `Action` → `app.rs` separation).

**Example shape (pattern confirmed via Tauri's official Android mobile-plugin docs, which use the identical `external fun` / `Java_<pkg>_<Class>_<method>` JNI convention — MEDIUM confidence as a direct precedent, HIGH confidence that the JNI naming/loading mechanics themselves are correct):**
```kotlin
class PlaybackService : Service() {
    init { System.loadLibrary("spotifast") }

    private external fun nativeOnPlay()
    private external fun nativeOnPause()
    private external fun nativeOnSkipNext()
    private external fun nativeOnDestroy()

    private val sessionCallback = object : MediaSession.Callback() {
        override fun onPlay() = nativeOnPlay()
        override fun onPause() = nativeOnPause()
        override fun onSkipToNext() = nativeOnSkipNext()
    }
    // onStartCommand/onCreate build the MediaSession + notification, call startForeground()
}
```
```rust
#[no_mangle]
pub extern "system" fn Java_dev_spotifast_PlaybackService_nativeOnPlay(
    _env: JNIEnv, _this: JObject,
) {
    // enqueue a PlayerCommand::Play on the existing backend.rs/player.rs channel
}
```

### Pattern 3: Service owns lifecycle, Activity/Rust core owns playback state — communicate, don't nest

**What:** The `PlaybackService` is a separate OS-managed component from the `NativeActivity`. It is *not* a child of the Activity and must not be architected as if Rust's `android_main` "owns" it. Instead: the Activity (via Rust, Pattern 1) *starts* the Service with `startForegroundService()`; from then on the Service and the long-lived Rust backend/player communicate as peers over the JNI boundary (Pattern 2 for Service→Rust, Pattern 1 for Rust→Service/notification updates), both ultimately driving the same `backend.rs`/`player.rs` state that already lives in its own tokio runtime, independent of any UI/Activity thread.
**When to use:** Always, for this app — it's required by Android's process model: the Service can legitimately outlive the Activity (screen off, app swiped from recents is a different case — see Anti-Pattern 2), but the single tokio runtime and librespot session in `backend.rs`/`player.rs` should be initialized once per *process*, not per Activity instance, and kept alive by the foreground Service's lifetime, not the Activity's.
**Trade-offs:** Requires a small amount of synchronization/singleton logic (e.g. an `OnceLock`/`static` holding the channel sender for backend commands) so that both the Activity-driven JNI calls and the Service-driven JNI calls reach the same running backend regardless of which component's JNI entry point fires first on process start. This is a new concern the desktop app never had (desktop has exactly one process, one window, one lifetime).

## Data Flow

### Control flow: cold start → background playback

```
User taps app icon
  → MainActivity (android-activity) created → android_main spawns thread
  → Rust: app.rs starts backend.rs tokio runtime + player.rs (as on desktop)
  → User presses Play in egui UI → ui/ emits Action::Play → app.rs applies it
  → app.rs (via jni_bridge.rs, Pattern 1) calls
      Context.startForegroundService(Intent(PlaybackService))
  → Android creates PlaybackService.onCreate()
      → Kotlin builds MediaSession + notification, calls startForeground()
      → Kotlin registers sessionCallback (forwards to Rust via external fun)
  → librespot/player.rs starts producing audio (unchanged from desktop)
  → User locks screen → Activity paused, Service keeps running (not tied to Activity)
  → User taps "pause" on lock-screen notification
      → Android calls sessionCallback.onPause()
      → Kotlin: nativeOnPause() → Java_..._nativeOnPause (Rust)
      → Rust sends PlayerCommand::Pause into the existing backend.rs channel
  → player.rs state changes → (new) a small state-change listener calls back into
      jni_bridge.rs (Pattern 1) to update the notification's play/pause icon and
      MediaSession playback state (PlaybackState.Builder)
```

### Key Data Flows

1. **User-interaction commands (system → app):** Android lock-screen/Bluetooth/notification controls → `MediaSession.Callback` (Kotlin, Pattern 2) → `external fun` → Rust `service_bridge.rs` → existing `backend.rs`/`player.rs` command channel. No new command vocabulary needed — these map 1:1 onto the same `Action`/command types the desktop UI already produces.
2. **Playback-state updates (app → system):** `player.rs` state changes → a thin listener/poll in `src/android/jni_bridge.rs` → JNI calls to update `MediaSession.setPlaybackState()` / notification `RemoteViews` or `NotificationCompat.Builder`. This is the one place genuinely new "glue" logic lives on the Rust side (the desktop app has no equivalent system-notification sync today, though it may already have OS media-key integration via a `fastframe-*` crate worth checking for reusable state-diffing logic).
3. **Credential read/write:** `credentials.rs` (existing dispatcher, gains Android arm) → `credentials_android.rs` → JNI calls to `KeyStore`/`Cipher`/`SharedPreferences` (Pattern 1, no Kotlin). Same function signatures as the macOS/Windows/Linux providers, so `how-it-connects.md`'s auth flow does not need to change shape, only gain a backing store.
4. **Audio focus:** `AudioManager.requestAudioFocus()` needs an `OnAudioFocusChangeListener` (Pattern 2 — lives in the same `PlaybackService` Kotlin class, or a second tiny class) → `onAudioFocusChange(focusChange: Int)` → `external fun` → Rust decides to duck/pause/resume via `player.rs`, mirroring whatever logic (if any) the desktop currently has for OS-level interruptions.

## Scaling Considerations

Not applicable in the traditional multi-user sense (single-user personal debug APK). The relevant "scale" axis here is **Android OS version / OEM behavior variance**:

| Scale axis | Low-risk path | Higher-risk path |
|---|---|---|
| Android 8-11 (API 26-30) | `startForegroundService` + `startForeground` within 5s is lenient | — |
| Android 12-14 (API 31-34, project's current target) | Standard foreground service rules apply; `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permissions required in manifest | OEM battery-optimization kills (Samsung/Xiaomi/etc.) are a known long-tail pitfall, not fixable purely in-app |
| Android 15+ (API 35+) | — | WebSearch (MEDIUM confidence, unverified against official changelog) surfaced reports of `AudioManager.requestAudioFocus()` behavior changes and background-audio hardening requiring a visible Activity or a non-`SHORT_SERVICE` foreground service; worth a dedicated Phase 6 spike if the dev device/emulator runs API 35+ |

## Anti-Patterns

### Anti-Pattern 1: Trying to avoid any Kotlin/Java code entirely

**What people do:** Attempt to implement `MediaSession.Callback` or `Service` purely via raw JNI tricks (e.g. `java.lang.reflect.Proxy` + a hand-rolled `InvocationHandler`) to honor a "zero Java" goal.
**Why it's wrong:** `InvocationHandler` is itself an interface requiring a concrete implementing class — there's no way to bootstrap this without at least one real class file already compiled into the APK. The reflection-proxy route is also undocumented for this use case, fragile across Android versions, and strictly more code/risk than just writing one small Kotlin class.
**Do this instead:** Accept one minimal Kotlin class (Pattern 2) for the handful of APIs that require subclassing; keep everything else in Rust (Pattern 1). This matches the project's own stated goal in R7 — "smallest possible native code, isolated" — not "zero native code."

### Anti-Pattern 2: Treating the foreground Service as owned/child of the Activity

**What people do:** Start the backend/player singleton from `android_main`/Activity `onCreate` and assume it's torn down and recreated together with the Service.
**Why it's wrong:** Android can destroy and recreate the `Activity` (rotation, backgrounding, low memory) independently of the `Service`, and vice versa the Service can be killed by the system while the Activity process concepts differ subtly. If `backend.rs`'s tokio runtime and librespot session are tied to Activity lifecycle, audio will cut out on rotation or when the user merely locks the screen — defeating AND-07/AND-09.
**Instead:** Initialize the backend/player once per process (a `OnceLock`/lazy static, same as how `android-activity` already treats `ndk_context`'s `AndroidContext` as process-global), and have *both* the Activity's JNI entry points and the Service's JNI entry points reach into that same shared state. The Service's `onStartCommand`/`onDestroy` govern whether playback *may* continue in the background and whether the notification exists — not whether the Rust runtime exists.

### Anti-Pattern 3: Picking the packaging tool before confirming Kotlin/Service support

**What people do:** Default to `cargo-apk` (the most commonly referenced tool in older Rust+Android tutorials) for Phase 1 because it's simplest for "draw a GL surface," without checking Phase 6 needs.
**Why it's wrong:** The original `cargo-apk` (rust-mobile/cargo-apk) has no documented mechanism for declaring a `<service>` manifest element or compiling custom Kotlin/Java sources to DEX (confirmed by reading its own docs — MEDIUM confidence, absence-of-feature claim). Discovering this in Phase 6 would force a packaging-tool migration mid-project, re-touching every earlier phase's build config.
**Instead:** Decide the Phase 1 packaging tool with Phase 6 in mind (see Build Order below).

## Integration Points

### External Services (Android system APIs)

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| `AudioManager` (focus request) | Rust via Pattern 1 for the request call; Kotlin `OnAudioFocusChangeListener` (Pattern 2) for the callback | Modern API wants `AudioFocusRequest.Builder` (API 26+); confirm current behavior on the actual target API level (R7/R9 risk — WebSearch surfaced unverified Android 15 regressions, MEDIUM/LOW confidence) |
| `NotificationManager` + notification channel | Rust via Pattern 1 (`createNotificationChannel`, `NotificationCompat.Builder`) or built inside the Kotlin `PlaybackService` at `onCreate` | Either side works since these are concrete builder classes; simplest to build it once in Kotlin alongside the Service it belongs to, and have Rust call a narrow "update now-playing text/art" JNI entry point for updates |
| `MediaSession` (platform `android.media.session`) | Kotlin shim owns the `MediaSession` instance + `Callback` (Pattern 2); Rust updates `PlaybackState`/metadata via Pattern 1 calls back into the held `MediaSession` object | Platform API avoids pulling in `androidx.media3` (Maven dependency, Gradle requirement); sufficient for lock-screen/Bluetooth, no Android Auto |
| `androidx.media3.session.MediaSessionService` (alternative) | Requires implementing `androidx.media3.common.Player` (Kotlin) that delegates every getter/command to Rust state | Lower risk of reinventing audio-focus/notification edge cases (Media3 handles both internally) but costs: a Gradle+Maven build (rules out `cargo-apk`/`cargo-apk2`'s no-Gradle mode), more Kotlin surface, and an extra abstraction layer translating Rust player state into `Player`'s synchronous getter contract. Recommended only if the platform-API route (row above) proves too fragile during Phase 6. |
| `java.security.KeyStore` ("AndroidKeyStore" provider) | Pure Rust via Pattern 1 — `KeyStore.getInstance("AndroidKeyStore")`, `KeyGenParameterSpec.Builder`, `Cipher.getInstance(...)`, ciphertext persisted via `SharedPreferences` | No subclassing needed; this is the cleanest integration point in the whole list |
| `keyring-core` (existing Rust dependency) | New `CredentialStore` impl in `credentials_android.rs`, registered via `keyring_core::set_default_store` at Android startup | **Gap found in research:** the one maintained Android-Keystore crate discovered, `android-keyring` (docs.rs), targets the older `keyring` crate's `CredentialBuilder`, not `keyring-core`'s `CredentialStore`/`Credential` traits the project already depends on. These are different crate families (same open-source-cooperative org, incompatible APIs per `keyring-core`'s own docs). Treat `android-keyring` as a *reference for the JNI Keystore calls*, not a drop-in dependency — Phase 4 should budget for writing a small first-party `CredentialStore` impl rather than assuming a ready-made provider exists. LOW confidence this gap still exists by the time Phase 4 starts; re-check both crates' latest versions then. |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| `src/ui/` ↔ `src/app.rs` | `Action` enum (existing) | Unchanged on Android |
| `src/app.rs` ↔ `src/backend.rs`/`src/player.rs` | Existing channel/call pattern into the tokio runtime | Unchanged on Android; Android JNI entry points (service_bridge.rs) feed into this same boundary rather than creating a parallel one |
| `src/android/service_bridge.rs` ↔ Kotlin `PlaybackService` | JNI, Java→Rust direction (`external fun` / `Java_<pkg>_<Class>_<method>` exported symbols) | Keep this the only Java→Rust direction; it should contain no logic beyond translating a callback into an existing command type |
| `src/android/jni_bridge.rs` ↔ Android system classes | JNI, Rust→Java direction (`jni` crate + `ndk-context`) | Must explicitly `attach_current_thread`/let the guard drop when called from a tokio worker thread, not just the `android_main` thread |
| `src/credentials.rs` ↔ `src/android/credentials_android.rs` | Existing provider-dispatch pattern (same shape as the macOS/Windows/Linux arms) | New arm only; no change to call sites elsewhere in the app |

## Build Order / Phase Dependencies

This directly affects the project's own phase plan (Fases 1, 4, 6):

1. **Phase 1 (build/packaging) must settle the packaging-tool question with Phase 6 in mind, not just Phase 1's own needs.** Concretely: confirm during Phase 1 whether the chosen tool (`cargo-apk2`, `cargo-ndk` + a minimal hand-written Gradle/Android-Studio module, or `xbuild`) can (a) compile and package a custom Kotlin `.kt` file to DEX, and (b) declare a `<service>` element with `android:foregroundServiceType` in the manifest. `cargo-apk2` (an actively maintained fork of the original, now-deprecated `cargo-apk`) advertises both capabilities without requiring full Gradle (MEDIUM confidence — confirmed via its `docs.rs` package description and `kotlin-examples/` directory, not yet hand-verified by building it). A minimal Gradle module via `cargo-ndk` gives the most headroom (any Maven dependency, including `androidx.media3` if Pattern 2's platform-API route proves insufficient) at the cost of more upfront build complexity. Recommendation: prefer **`cargo-ndk` + a minimal Gradle/Android-Studio module** for this project specifically, because it keeps the door open to `androidx.media3` without a later migration, and Gradle/Kotlin tooling is already confirmed present in the dev environment (Java 25 OpenJDK, per `PROJECT.md`); fall back to `cargo-apk2` only if Gradle setup proves to be the bigger time sink in Phase 1.
2. **`src/android/jni_bridge.rs` (Pattern 1, Rust→Java) has no dependency on the Kotlin shim existing yet.** It can be built and exercised (e.g. for `AudioManager` lookups, or a first proof-of-concept Keystore read/write) as soon as `ndk-context` is wired up in Phase 1/2, well before Phase 4 or 6 formally start. Consider a small Phase 1/2 spike here to retire risk early.
3. **Phase 4 (login/credentials) depends only on step 2 above**, not on the Service/MediaSession work in Phase 6. `credentials_android.rs` can be built standalone against `java.security.KeyStore` with no Kotlin class at all.
4. **Phase 6 (background/media controls) is the only phase that needs the Kotlin `PlaybackService` shim (Pattern 2).** It depends on: the packaging tool decision from step 1 (must support compiling and bundling this class), and the existing `backend.rs`/`player.rs` command channel being reachable from a JNI entry point (straightforward, same shape as `app.rs` calling into it today).
5. **Decide platform `MediaSession` vs. `androidx.media3.session.MediaSessionService` before writing `PlaybackService`**, not during. The platform API is less code and matches "smallest native surface," but Media3 is lower-risk for audio-focus/notification edge cases if early manual testing in Phase 6 reveals the platform API is too fiddly. This is a judgment call to make explicit at the start of Phase 6 rather than drift into mid-phase, since it changes whether Gradle/Maven dependencies are needed.
